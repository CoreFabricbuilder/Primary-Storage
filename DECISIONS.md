# Technical decisions

- The MVP runs directly from `index.html` with plain HTML, CSS and classic JavaScript. This removes local build and server requirements and avoids browser `file://` module restrictions.
- IndexedDB stores the active model and photo Blobs. JSON backup/restore is explicit because browser profile data is not a durable external backup.
- The topology uses dependency-free SVG with pan, zoom, selection and filtering. It can be replaced behind `topology.js` if a graph library becomes necessary.
- Time state, perspective and evidence classification are separate fields. Readiness status changes do not change evidence classification.
- Vendor observations enter through a local snapshot adapter and require explicit architect review before a sourced Observed record is appended. They do not become confirmed automatically.
- No customer documents, photographs, configurations or credentials are stored in Git. The repository holds synthetic seed data and a defensive `.gitignore`.
- Phase 2 uses sparse `branchAttributes` for Physical and Logical observations. A missing value remains Unknown; current observations do not overwrite inherited pattern targets.
- Branch patterns are editable reusable intent. Three synthetic examples demonstrate different targets without asserting any final client pattern.
- Branch evidence metadata and photograph Blobs are linked by stable photo ID; photo changes are atomic across both IndexedDB stores. Non-photo evidence stores references only.
- The estate matrix shows classifications and partial coverage rather than a project percentage. Current-versus-target deltas are comparisons, not validation or acceptance results.
- Schema 1 browser workspaces and JSON backups migrate to schema 2. Existing evidence classifications are preserved.
- Phase 3 keeps fact-validation records separate from deployment assurance records. The new `assurance.js` module evaluates fixed comparators (quantity, set, exact value) without AI or vendor APIs.
- Baselines snapshot Design Intent and become immutable when activated. Observed and As-Built records append with source; runs snapshot their rule results and provenance.
- Critical mandatory failures always fail the acceptance gate, even with an approved exception. Unknown mandatory results block acceptance; noncritical approved exceptions may permit explicit conditional acceptance.
- Synthetic LAN, Wi-Fi, SD-WAN, physical, routing and management rules demonstrate the six rule categories. Missing target or observation values remain Unknown.
- Schema migration adds the rule catalogue and gates to an existing workspace without injecting synthetic observations, baselines or runs. New demonstration workspaces alone contain synthetic assurance examples.
- Phase 4 keeps Dashboard credentials in macOS Keychain. An optional collector makes fixed-host read-only GET requests and uses built-in JavaScript for Automation to allowlist snapshot fields; the browser remains offline.
- A Meraki snapshot must be mapped to a branch and staged. Per-candidate Apply or Dismiss decisions retain provenance. Applying never changes a baseline, earlier run or confirmation.
- Schema 4 adds Meraki batch/candidate collections. Existing schema 3 workspaces migrate with empty vendor collections; only the synthetic demo starts with staged candidates.
- The portfolio uses a locally bundled XLSX parser and two-sheet projection. The source workbook file is never stored; displayed cell values and row references are retained in IndexedDB and JSON backup.
- Repeat imports use source identity keys, mark removed rows without deleting enrichment, and log import changes. An identity edit may appear as a removal plus a new record; duplicate identities are warned about.
- Source Planning Status, timeline markers and parsed dates do not set Architecture Gates. Architect-owned mappings, activity links and gates remain separate from source rows.
- Transformation domain labels are a finer matrix taxonomy linked to existing architecture domains. Object mappings reference existing architecture IDs; HLD/LLD and validation requirements can use explicit references.
- The bundled parser is `@e965/xlsx` 0.20.3 (Apache 2.0). No CDN or developer tooling is needed at runtime.
- Phase 6 uses a separate SD-WAN validation history rather than changing the existing assurance rule catalogue, preserving historical run completeness and immutable results.
- The optional Catalyst SD-WAN companion uses a Keychain-backed Manager session and fixed GET data routes. It projects allowlisted site facts to JSON outside Git; unsupported queries produce coverage flags and Unknown checks.
- Branch and Campus mapping is explicit. Candidate Apply records Observed only; targets are separately versioned Design Intent. Critical mandatory failures block the combined Branch state regardless of other passing checks.
- Phase 7 derives service paths from topology links for the selected Current, Transition or Future state. Paths are labelled logical design candidates, with classification and source; they do not claim observed traffic or security policy.
- Segmentation uses typed sourced links. Site-related inventory and routing are shown as context only, preserving the distinction between co-location and proven membership.
- An architect can create an As-Built Baseline only from a passing accepted deployment; the latest SD-WAN run available at acceptance, if present, must be ready. The new record freezes observed values without changing Design Intent, prior runs or future observations.
- Drift compares observations recorded after acceptance. Missing later evidence is not No Change. Expected and Approved Change require an architecture decision and rationale; Approved Change requires a decision approved at review time. Reviews never remediate or rewrite baseline values.
- The pre-SD-WAN branch report is an append-only Current/Observed source snapshot. UID matching preserves leading zeros; ambiguous cells and incomplete rows are flagged without correcting or inferring targets. New branches use an all-null unassigned pattern and Unknown LLD rows. Re-import preserves architect-owned records and accepted baselines.
- The import offers explicit clean replacement or merge. Clean replacement clears the old workspace and photos atomically after confirmation. Customer CSV files and JSON backups remain outside Git; only synthetic test rows are committed.
- The Scenario Explorer applies an existing Branch Pattern hypothetically across branches, grouping derived gaps by architecture area. It does not mutate the model or introduce a second target store. Saved design options remain in the Branch Pattern Catalogue.
- Scenario gaps retain Current classification and source, and Unknown remains explicit. A Current Deployment Report AP count can be compared as Observed, while connectivity media and subnet strings remain source context rather than inferred SD-WAN transports or validated segments.
- A browser workspace with a newer schema is left untouched; startup displays a persistent version-specific error so users know to open a current app copy. Other startup errors retain their underlying message instead of all appearing as an IndexedDB failure.
